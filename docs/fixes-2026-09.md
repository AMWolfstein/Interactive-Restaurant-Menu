## ١) الباج الأخطر: قواعد الطلب كانت في المتصفح بس

أي حد يبعت `POST /api/orders` مباشرةً كان بيعدّي **كل** إعدادات المحل: يطلب
والمحل مقفول، بنوع طلب الأدمن قافله، تحت الحد الأدنى، والسلة متقفلة خالص،
وببيانات عميل ناقصة.

### الحل — ٣ طبقات

1. **[`lib/order-rules.ts`](../lib/order-rules.ts)** (جديد) — دوال نقية بتفرض
   القواعد بالترتيب: السلة → المحل مفتوح → نوع الطلب → بيانات العميل →
   الحد الأدنى العام → الحد الأدنى للمنطقة.
2. **`createOrder`** في [`lib/server-database.ts`](../lib/server-database.ts) —
   بتتنادى في **السائقين الاتنين** (Supabase وملف التطوير) فالسلوك واحد.
3. **`place_order`** في [`supabase/schema.sql`](../supabase/schema.sql) — نفس
   القواعد في SQL كخط دفاع أخير، بتشتغل حتى لو حد نادى Supabase REST مباشرةً.

> **نقطة مهمة:** التحقق القديم كان بيبص على `autoSchedule` بس، يعني **مفتاح
> القفل اليدوي في لوحة التحكم ما كانش بيمنع أي طلب على السيرفر**. دلوقتي
> `effectiveStoreOpen` بتغطي الحالتين.

### التحقق بالتشغيل

اتعمل سيرفر حقيقي واتبعتت طلبات فعلية:

| الحالة | قبل | بعد |
|---|---|---|
| طلب سليم | 201 | **201** ✅ |
| تحت الحد الأدنى (٣٠ ج والحد ٨٠) | 201 ❌ | **400** «أقل طلب 80 ج.م» |
| من غير اسم | 201 ❌ | **400** «اكتب الاسم بالكامل» |
| رقم موبايل ناقص | 201 ❌ | **400** «رقم الموبايل مش كامل» |
| المحل مقفول يدوياً | 201 ❌ | **409** «المحل مقفل حالياً» |
| السلة مقفولة | 201 ❌ | **409** «الطلب من الموقع مقفول حالياً» |
| نوع طلب مقفول | 201 ❌ | **400** «نوع الطلب ده مش متاح حالياً» |
| طلب سليم بعد رجوع الإعدادات | — | **201** (مفيش false positives) |

كمان اتأكدنا إن `salesCount` فضل **١** بعد الرفضات كلها — يعني العدّاد
مابيتزوّدش على طلب مرفوض (ده كان باج في سائق الملف: العدّاد كان بيتزوّد
جوه اللوب قبل ما التحقق يخلص).

## ٤) الـ Optimizations

| التحسين | الأثر |
|---|---|
| `place_order` بتجمّع المبيعات وبتطبّقها مرة واحدة | كان O(أسطر × منتجات) **والصف متقفول** — طلب ١٠ أصناف على كتالوج ٣٠٠ منتج = ٣٠٠٠ عملية |
| فهرس على `normalize_phone(data#>>'{customer,phone}')` | `customer_orders` كانت sequential scan على كل الطلبات |
| `list_catalog_backups` بتعدّ في قاعدة البيانات | كان بينزّل كتالوج كامل لكل نسخة من الـ١٥ عشان رقمين |
| الفحص الدوري بيقف والتاب مخفي (`usePoll`) | ٤ لوحات كانت بتضرب السيرفر كل ٣٠–١٢٠ ثانية للأبد حتى والتاب مقفول |
| `manifest`/`sitemap`/`icons` كاش قصير بدل `force-dynamic` | كان استعلام قاعدة بيانات مع كل طلب أيقونة |
| `next/image` للـ Hero وكروت المنتجات | WebP/AVIF وأحجام حسب الشاشة — الزباين على الموبايل |
| `fetchAdminOverview` ٢٠٠ طلب بدل ٥٠٠ | كل طلب جواه JSON كامل، والنداء بيتكرر كل ٣٠ ثانية |
| `TextEncoder` بدل `new Blob` في `sizeOf` | كان بيعمل نسخة كاملة من الـ JSON عشان عدّاد |
| تسريب مؤقّت في `menu-store-core` | كان `setInterval` دائم بيجيب الكتالوج كل دقيقة للأبد |
| `ES2022` بدل `ES2017` | بوليفيلات أقل وباندل أصغر |
| ترقية vitest 5 + supabase-js | سد ثغرة `@vitest/mocker` — `npm audit` نضيف |

## ٥) حاجات **ما اتعملتش** عن قصد

| البند | السبب |
|---|---|
| نقل `salesCount` لجدول منفصل (بند ٨ في الخطة) | تغيير هيكلي كبير بيمس شكل البيانات والـ realtime والأدمن. حسّنا الجزء الساخن (تمريرة واحدة بدل O(n×m)) من غير ما نكسر الشكل. يستاهل PR لوحده |
| `rate-limit` على Upstash/Redis | محتاج خدمة خارجية وقرار من صاحب المشروع. حطّينا سقف للمفاتيح وشيلنا الـ`setInterval` الدائم ووثّقنا الحد بوضوح |
| CSP بـ nonce بدل `unsafe-inline` | محتاجة middleware وإعادة هيكلة السكربت بتاع الثيم — تغيير محفوف بمخاطر كسر الهيدريشن. اتوثّقت في التقرير |
| `next` 16.3.5 → 16.3.6 | Next نفسه مش في `npm outdated` كـ wanted (الـlock مثبّت على 16.3.5) والترقية مش ضرورية أمنياً. `@next/eslint-plugin-next` اتحدّث |
| توحيد الـ polling في ستور واحد | خلّينا كل لوحة بمصدرها لكن وقّفنا الهدر الحقيقي (التابات المخفية). التوحيد الكامل إعادة هيكلة أكبر من فايدتها دلوقتي |
