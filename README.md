# 🛍️ Interactive Store Catalog — Full Stack (Next.js + Firebase)

تطبيق كتالوج منتجات لمحل، عربي **Full Stack**: واجهة عملاء RTL + لوحة تحكم + باك إند حقيقي يحفظ
الكتالوج والطلبات في Cloud Firestore.

## المميزات

- كتالوج RTL سريع ومتجاوب: بحث، أقسام، سلة، وإرسال الطلب على واتساب **برقم طلب قصير** زي `BF-7K4P2`.
- **صفحة فواتير للموظفين `/invoices`** منفصلة عن لوحة التحكم: دخول خاص، قائمة الطلبات لحظية
  (الجديد أولاً)، تفاصيل الطلب، وتوليد فاتورة PNG للتحميل أو الطباعة أو المشاركة على واتساب.
- **دور `invoice_staff`**: للطلبات والفواتير. تعديل الكتالوج والإعدادات متاح للأدمن، والصلاحيات متحققة على السيرفر.
- **محل تيك-أواي بدون طاولات**: نوعين طلب بس — استلام من المحل (الافتراضي: تشتري وتمشي) أو
  توصيل لباب البيت. نوع «من داخل المحل» اتشال نهائياً من الواجهة والباك إند، والطلبات القديمة
  المسجّلة بيه بتظهر في اللوحة بعلامة «قديم».
- **دخول لوحة التحكم حصرياً بـ Firebase Authentication (إيميل + باسورد)** من الحساب الموجود في
  `Authentication → Users`. مفيش أي دخول محلي أو رقم سري في المشروع.
- كل API خاص بالأدمن بيتحقق من **Firebase ID token على السيرفر** — أي طلب من غير توكن صالح بيرجع `401`.
- رفع صور المنتجات إلى Cloudinary مع الاسم والوصف والسعر والوزن والمورد.
- سعر قديم وجديد مع حساب نسبة الخصم تلقائياً وعداد اختياري يُدخل باليوم والشهر والسنة.
- قسم «الأكثر مبيعاً» يُرتّب تلقائياً من بيانات الطلبات الفعلية، بدون ترتيب يدوي.
- واجهة وإعدادات عربية فقط، مع مفضلة محفوظة على جهاز الزائر وإمكانية إعادة آخر طلب بضغطة واحدة.
- تبويب عروض حي، وفرز بالسعر أو الأحدث، مع إيقاف الخصم تلقائياً بعد تاريخ انتهائه.
- Hero carousel قابل للإدارة من لوحة التحكم، مع إيقاف تلقائي عند تمرير المؤشر وخيارات تنقّل واضحة.
- صفحة QR محلية قابلة للتنزيل والطباعة (`/qr`) ومنيو/كتالوج للطباعة أو الحفظ PDF (`/menu`) — بدون خدمة QR خارجية.
- اختيار من لوحة التحكم بين العرض التفصيلي الحالي أو شبكة من 3 منتجات، مع تصفية كل منتجات المورد بالضغط على اسمه.
- تسجيل الطلب قبل فتح رسالة واتساب، مع سجل للطلبات داخل لوحة التحكم.
- **تبويب «الطلبات»**: كل الطلبات المسجّلة مع فلاتر (حالة/نوع/فترة) وبحث بالاسم أو الموبايل أو رقم
  الطلب، وإلغاء الطلب أو إرجاع الملغي جديد (أي طلب جه من الموقع هيتنفذ — توصيل أو استلام)،
  وتصدير CSV متوافق مع الإكسل العربي.
- **تنبيه صوتي ووميض في عنوان التاب** مع أي طلب جديد على أي تبويب مفتوح في اللوحة، مع عداد أحمر
  على تبويب الطلبات — تحديث لحظي عبر Realtime مع فحص دوري احتياطي.
- **فتح وقفل أوتوماتيك**: جدول مواعيد أسبوعي (بتوقيت القاهرة) بيشغّل ويقفل المحل لوحده، بيدعم
  الفترات اللي بتعدي نص الليل، والسيرفر بيرفض أي طلب وقت القفل، مع إظهار موعد الفتح القادم للعميل.
- **مناطق توصيل برسوم مختلفة**: لكل منطقة رسومها وحدها الأدنى، والعميل يختار منطقته في السلة —
  والرسوم بتتحسب على السيرفر ضد التلاعب، والمنطقة بتتسجّل مع الطلب وتظهر في الفاتورة.
- **طرق دفع**: كاش / فودافون كاش / انستاباي… العميل يختار في السلة، والطريقة بتتسجّل مع الطلب
  وتظهر في الفاتورة وتبويب الطلبات، وكمان في فوتر الموقع.
- **تحليلات مبيعات** في «نظرة عامة»: إيراد اليوم/الأسبوع/الشهر، متوسط قيمة الطلب، رسم بياني
  لإيراد آخر ١٤ يوم، وأعلى المنتجات بالإيراد (الطلبات الملغية مستثناة).
- إشعارات Web Push اختيارية للعروض والمنتجات الجديدة، مع زر واضح لإلغاء الاشتراك.
- نسخ احتياطي يدوي ويومي مجدول مع الاحتفاظ بآخر 30 نسخة واسترجاع من لوحة التحكم.
- حفظ لحظي مركزي: تعديل الأدمن يظهر لكل العملاء على كل الأجهزة، ولافتة واضحة عند انقطاع الإنترنت.
- **الهوية بتترسم من السيرفر**: اسم المحل ولونه وستايله وخطه بيجوا مع أول HTML من
  قاعدة البيانات — فمفيش ظهور للشكل الافتراضي («محل البركة» البرتقاني) قبل ما
  بيانات المحل تتحمّل.

## الباك إند

| المسار | الوصف | الصلاحيات |
| --- | --- | --- |
| `GET /api/menu` | قراءة الكتالوج | عام |
| `PUT /api/menu` | حفظ الكتالوج | أدمن (Firebase ID token) |
| `POST /api/orders` | تسجيل الطلب قبل فتح رسالة واتساب | عام |
| `GET /api/admin/overview` | سجل الطلبات + حالة التخزين | أدمن (Firebase ID token) |
| `PATCH /api/admin/orders` | تحديث حالة طلب (جديد/ملغي) | أدمن (Firebase ID token) |
| `GET /api/admin/session` | التحقق من جلسة الأدمن على السيرفر | أدمن (Firebase ID token) |
| `GET /api/invoices/session` | التحقق من جلسة شاشة الفواتير + الدور | أدمن أو `invoice_staff` |
| `GET /api/invoices/orders` | طلبات شاشة الفواتير (نفس جدول `orders`) | أدمن أو `invoice_staff` |
| `PATCH /api/invoices/orders` | تحديث حالة طلب من شاشة الفواتير | أدمن أو `invoice_staff` |
| `POST /api/loyalty` | رصيد «كاشك» لرقم موبايل (للعرض في السلة) | عام (محدود بـ15/دقيقة) |
| `GET /api/admin/customers` | قائمة عملاء «كاشك» وأرصدتهم | أدمن (Firebase ID token) |
| `GET /api/admin/backups` | قائمة النسخ الاحتياطية أو استرجاع نسخة بـ`?id=` | أدمن (Firebase ID token) |
| `POST /api/admin/backups` | إنشاء نسخة احتياطية فورية | أدمن (Firebase ID token) |
| `POST /api/push-subscription` | تسجيل جهاز لاستقبال إشعارات الكتالوج | عام مع حدود للمعدّل |
| `DELETE /api/push-subscription` | إلغاء تسجيل الجهاز | عام مع حدود للمعدّل |
| `GET /api/cron/backup` | نسخة احتياطية يومية (Vercel Cron) | `CRON_SECRET` |

Firebase Admin بيتحقق من الـ ID token والدور على السيرفر. وقواعد Firestore بتسمح
للمتصفح يسمع إشارات تغيّر الكتالوج والطلبات حسب صلاحياته. البيانات نفسها بتعدّي
من الـ API، بما فيها طلبات العملاء والنسخ الاحتياطية واشتراكات الإشعارات.

### قواعد قبول الطلب

السيرفر بيقرأ الكتالوج ضمن معاملة Firestore واحدة، ويتأكد من المواعيد، ونوع الطلب،
والمنتجات المتاحة، والحد الأدنى، ومنطقة التوصيل، وبيانات العميل. السعر والرسوم وخصم
كاشك بيتحسبوا من الكتالوج ورصيد العميل وقت الطلب. المعاملة بتسجل الطلب وتحدّث
الرصيد وعدادات المبيعات مع بعض. [قواعد الطلب](lib/order-rules.ts)

## إعداد Firebase

1. اعمل مشروع Firebase وفَعّل **Cloud Firestore** في وضع Native، وفعّل طريقة تسجيل الدخول
   **Email/Password** في Authentication. سجّل Web App عشان تجيب قيم المتصفح.
2. اضبط متغيرات [.env.example](.env.example) في بيئة النشر. السيرفر يحتاج بيانات اعتماد
   Firebase Admin لنفس المشروع، عبر متغيرات الحساب الخدمي أو Application Default Credentials.
3. انشر قواعد Firestore والفهارس من جذر المشروع. استنى فهرس طلبات العميل يبقى جاهز قبل اختبار البحث.

   ```bash
   npx firebase-tools deploy --only firestore:rules,firestore:indexes --project YOUR_FIREBASE_PROJECT
   ```
4. اعمل حساب كل مستخدم في **Authentication → Users**، وبعدها عيّن الدور من جهاز عنده
   بيانات اعتماد Firebase Admin عبر `GOOGLE_APPLICATION_CREDENTIALS` أو ADC:

   ```bash
   npm run firestore:role -- owner@your-store.example admin
   npm run firestore:role -- staff@your-store.example invoice_staff
   ```

| الدور | لوحة التحكم `/admin` | شاشة الفواتير `/invoices` |
| --- | --- | --- |
| `admin` | مسموح | مسموح |
| `invoice_staff` | مرفوض | مسموح |
| حساب من غير دور | مرفوض | مرفوض |

الفواتير بتستخدم نفس الطلبات اللي في لوحة التحكم، وبتولّد صورة PNG من السعر
والإجمالي المحفوظين وقت تسجيل الطلب. رقم الطلب وصورة الفاتورة القديمة بيفضلوا صالحين
بعد تعديل سعر المنتج.

### نقل البيانات من Supabase

أداة النقل بتنسخ الكتالوج والطلبات وأرقامها وأرصدة كاشك وعدادات المبيعات والنسخ
الاحتياطية واشتراكات Web Push. احتفظ بمفاتيح VAPID الحالية عشان الاشتراكات المنقولة
تفضل شغالة. اضبط `SUPABASE_MIGRATION_URL` و`SUPABASE_MIGRATION_SERVICE_KEY`
على جهاز النقل فقط، واضبط `FIREBASE_PROJECT_ID` وبيانات اعتماد Firebase Admin
هناك. استخدم مشروع Firestore فاضي لاستيراد أول نسخة.

```bash
npm run firestore:migrate             # يطبع عدد السجلات من غير كتابة
npm run firestore:migrate -- --apply  # يكتب السجلات في Firestore
```

أوقِف الكتابة في Supabase أثناء النقل النهائي لتثبيت لقطة المصدر. الأداة تقدر تكمل
بعد انقطاع باستخدام نفس الأمر، وبتتخطى السجلات الموجودة. راجع الأعداد والطلبات
والرصيد في Firebase قبل تحويل حركة الموقع. حسابات المستخدمين وكلمات السر ليها
إعداد منفصل في Firebase Authentication. اعمل الحسابات وعيّن أدوارها قبل التحويل.

## 🎁 نظام «كاشك» (مكافأة العملاء)

لما مشتريات العميل توصل مبلغ معيّن (٥٠٠٠ ج افتراضياً) بياخد خصم (٥٪) على
**الفاتورة اللي بعدها**، وبعدها الرصيد يتخصم منه المبلغ ده وتبدأ دورة جديدة.
الزيادة فوق العتبة بتترحّل للدورة الجديدة — العميل مش بيخسرها.

- **مين العميل؟** رقم الموبايل. الأرقام بتتوحّد تلقائياً (`+20…` و `0…` و
  `0101 234 5678` كلها نفس العميل) في `lib/loyalty.ts`.
- **الرصيد بيتجمّع من قيمة المنتجات بس** — التوصيل ورسوم الخدمة مش داخلين في
  الرصيد ولا بياخدوا خصم.
- **الحساب على السيرفر داخل معاملة Firestore** مع تسجيل الطلب.
- **الإلغاء بيعكس الأثر:** الطلب الملغي بيتشال من الرصيد، ولو كان صرف مكافأة
  المكافأة بترجع للعميل — فمحدش يقدر يجمع رصيد بطلبات وهمية.
- **الإعدادات** من لوحة التحكم → «الطلب والأسعار» → «نظام كاشك» (تفعيل/إيقاف،
  المبلغ، النسبة، الاسم المعروض).
- **تبويب «العملاء»** في اللوحة: بحث برقم الموبايل أو الاسم **على السيرفر**
  (مش مقيّد بآخر ٥٠٠ طلب)، وكل عميل بتشوف رصيده وتاريخ مشترياته الكامل.

> **بداية ببيانات فارغة:** أدخل أقسامك ومنتجاتك من لوحة التحكم.
>
> **نقل مشروع Menyu القديم:** من «البيانات» ارفع ملف JSON القديم كما هو وراجع المعاينة قبل الحفظ.
>
> **التحديث اللحظي:** Firestore بيتابع علامات تغيّر الكتالوج والطلبات، مع فحص دوري احتياطي.

## متغيرات البيئة

استخدم [.env.example](.env.example) للتشغيل المحلي. في Vercel حط نفس القيم المطلوبة في
**Project Settings → Environment Variables**. خلي بيانات اعتماد Firebase Admin ومفتاح
VAPID الخاص و`CRON_SECRET` في متغيرات السيرفر.

### إعداد النسخ التلقائي وإشعارات Push

1. جهّز `NEXT_PUBLIC_VAPID_PUBLIC_KEY` و`VAPID_PRIVATE_KEY` و`VAPID_SUBJECT`.
   لمشروع جديد استخدم `npx web-push generate-vapid-keys`.
2. أضف `CRON_SECRET`. ملف `vercel.json` يستدعي `/api/cron/backup` يومياً الساعة
   02:15 UTC. الموقع بيحتفظ بآخر 30 نسخة، ويدعم النسخ اليدوي والاسترجاع من «البيانات».
3. اضبط `NEXT_PUBLIC_SITE_URL` كرابط الإنتاج للـ canonical links و`/sitemap.xml`.

### إعداد Cloudinary للصور

1. من Cloudinary افتح **Settings → Upload → Upload presets**.
2. أنشئ preset من نوع **Unsigned** ويفضّل تقييده بملفات الصور وبحد أقصى 5MB.
3. أضف اسم الـ cloud والـ preset في متغيرات البيئة الموضحة فوق.
4. أعد نشر المشروع. بعدها رفع اللوجو وصورة الغلاف وصور المنتجات من لوحة التحكم
   يرفعها مباشرةً إلى Cloudinary ويحفظ رابط `https` فقط بدل تخزين الصورة داخل بيانات الكتالوج.

> اسم الـ cloud والـ unsigned preset قيم عامة مصممة للاستخدام من المتصفح؛ لا تضف
> `API Secret` أو `API Key` إلى متغيرات تبدأ بـ `NEXT_PUBLIC_`.

#### نسيت حساب Cloudinary؟ اعرف اسم الـ cloud من صورك

كل رابط صورة مرفوعة على Cloudinary جواه اسم الحساب (cloud name)، وده اللي بيحدد
الحساب. شغّل الأمر ده وهو هيستخرجه من بيانات الكتالوج:

```bash
npm run cloudinary:whoami                 # يقرأ من الموقع الشغال
npm run cloudinary:whoami backup.json     # أو من نسخة احتياطية نزّلتها
```

بعد ما تعرف الاسم:

1. جرّب **Forgot password** على <https://cloudinary.com/users/login> بكل إيميل عندك —
   الإيميل الصاحب للحساب هو الوحيد اللي هتوصله رسالة.
2. لو مفيش فايدة، ابعت لـ `support@cloudinary.com` واذكر الـ cloud name ومثال
   لرابط صورة — دي أول حاجة بيطلبوها للتأكد من ملكية الحساب.
3. بعد الدخول: **Settings → My Profile** واعمل باسورد مباشر، عشان متبقاش معتمد
   على تسجيل الدخول بجوجل لوحده.

## التشغيل محلياً

```bash
npm ci
cp .env.example .env.local
npm run dev
```

اضبط بيانات Firebase في `.env.local`، أو استخدم الـ Emulator Suite بمشروع
`demo-restaurant-menu` ومفتاح متصفح تجريبي. فعّل متغيرات المحاكيات الأربعة الموجودة
في المثال، وشغّل Auth وFirestore في طرفية تانية قبل تشغيل التطبيق:

```bash
npx firebase-tools emulators:start --project demo-restaurant-menu --only auth,firestore
```

- الموقع على `http://localhost:3000`
- لوحة التحكم على `http://localhost:3000/admin`
- شاشة الفواتير على `http://localhost:3000/invoices`

لو مسحت متغيرات Firebase بالكامل، الموقع يقدر يعرض الكتالوج ويجرب الطلبات في ملف JSON محلي.

## التحقق

الـ CI بيستخدم Node.js 22. الـ Firebase Web SDK متثبّت على 12.19.0 مع تبعياته
المتوافقة مع Node 22. راجع التثبيت ده عند ترقية Node والـ Firebase SDK مع بعض.

```bash
npm run typecheck   # فحص الأنواع
npm run lint        # فحص الأسلوب
npm test            # الاختبارات (vitest)
npm run build       # بناء الإنتاج
```

الأربعة بيتنفّذوا تلقائياً على كل push و pull request عن طريق
[`.github/workflows/ci.yml`](.github/workflows/ci.yml).
